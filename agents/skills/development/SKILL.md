# Development — 开发维护规则

适用于所有项目的开发任务，与项目自身规范及领域 skill 同时执行。

## 0. 开发前同步远端基线

避免在过期代码或过期开发规则上开始工作。以下是修改前的必过关卡，不是事后补做的检查；适用于功能开发和环境修复，不能因为当前目录叫 master、工作区干净或另一会话已 fetch 就跳过：

- 检查 `git status`、当前分支和 `git worktree list`，识别已有改动、未推送提交及其他会话的工作区；不得覆盖、丢弃或擅自搬移这些工作。
- 执行 `git fetch origin`，确认 origin 的默认主分支（如 `main` / `master`），以本次 fetch 后的 `origin/<主分支>` 为基线；不能把本地同名主分支或未刷新的远端引用当作最新代码。项目明确要求其他目标分支时，以该远端目标分支为准。
- 以项目规定的开发目标为准，不盲从 `origin/HEAD`（它可能指向生产分支）。修改前记录工作目录、任务分支、远端目标及其 SHA；新建分支后用 `git rev-parse HEAD` 与 `git rev-parse origin/<目标分支>` 核对起点一致。简短向用户说明基线，不以“已同步”代替实际核验。
- 从该最新远端基线创建本任务的独立开发分支，优先用 `git worktree add -b <任务分支> <新目录> origin/<主分支>` 创建隔离工作树，并将会话工作目录切换过去；不在主分支、部署分支或 detached HEAD 上直接开发。
- 在新工作目录重新读取适用的 `AGENTS.md`、开发 Skill 和相关项目文档，避免继续沿用旧工作树中的规则。
- 在最新基线上重新核对问题及相关实现/修复记录，确认远端是否已经解决；旧会话日志只作为线索，不据此重复修复或照搬旧配置。
- 当前工作区已有改动时，优先保持原状并另建工作树。需要将已有任务改动迁移到最新基线时，先核对归属和差异；迁移会影响其他工作或无法安全判断时，先向用户确认。禁止为同步基线自动 reset、清理、stash 或强制 checkout。
- 同一任务的后续轮次可以继续使用其开发分支/worktree，无需反复创建。继续开发及提交/推送前再次 fetch，核对目标分支是否前进；如已前进，先评估差异，在保留现有工作的前提下安全同步并复测，不擅自 rebase 已发布提交或强制推送。
- fetch 失败、origin 不存在或目标分支无法确定时，明确告知阻塞；未经用户同意，不以旧基线继续修改。用户明确指定旧提交或要求沿用现有分支时，说明基线偏离后按其要求执行。

## 0.1. 本机环境修复与跨 worktree 复用

- 先检查现有工具链、用户级配置、共享依赖缓存和容器状态；区分 PATH/版本管理器未激活、网络源、依赖缺失与应用故障，不重复安装已有工具，不停止其他任务的服务。
- 地域网络、镜像源或个人工具偏好优先用工具原生的用户级配置；不足时再用仓库外的最小启动入口/override。集中一处维护，跨 worktree 生效，不依赖向每个新工作树复制忽略文件。
- 根据运行机器的实际网络选择源，海外优先官方源；保留团队成员的国内镜像选择。不要仅为本机问题修改公共仓库、共享默认值或锁文件；确需团队级修复时先说明必要性与影响，再按授权处理。
- 优先复用项目现有构建与启动流程，避免维护平行的一整套配置；共享可复用的依赖缓存，同时隔离各任务的数据库、运行状态和端口。
- 不假设终端与 Docker daemon 共享文件系统；先在容器内确认源码实际可见。初始化数据前检查种子是否调用外部服务，优先使用项目已有的本地 stub，避免把自动 seed 当成无副作用的建库步骤。
- 修复后实际构建并启动本地容器，验证应用响应及必要依赖；再从另一干净 worktree 验证配置自动生效。配置解析成功不等于环境可用，后台构建未完成不等于验收通过；阻塞和未验证项如实说明。
- 本机验证不授权连接生产环境；不复制生产凭据作为启动捷径。

## 1. 图片不进入源码文档

- 不向源码文档目录添加或更新截图、照片、渲染图等图片文件，也不在文档中嵌入图片。
- 验证截图存到仓库外临时目录，或项目明确忽略的测试产物目录；需要分享时使用 PR 附件或外部存储，不以提交图片到 Git 代替。
- 不添加把截图写进 `docs/` 等文档目录的脚本、测试辅助方法或环境变量入口；已有此类入口时，在相关改动中删除。
- 业务实际需要的图片资源、测试必需的图像夹具不属于文档截图，不因本规则误删。
- 清理限于当前改动和直接相关的引用；不擅自全仓库删图，也不为清理图片擅自重写 Git 历史。

## 2. 源码文档只描述当前状态

- 优先原地更新已有文档，替换过时段落，不追加“之前怎样、此次怎样、现在修好了”等过程描述。
- 不在源码文档累积变更日志、逐轮测试结果、会话记录、已完成待办或旧实现说明；过程信息放 commit / PR，历史交给 Git。
- 只保留理解当前契约、使用方法、限制和必要设计决策所需的内容，避免跨文档重复。
- 当前仍支持的兼容行为、真实边界和操作指引应保留；不要把它们误判为过程记录。
- 若项目明确要求进行中计划或决策文档，按其约定维护，但不把这些过程搬进现状文档。

## 3. 废弃功能与测试一起删除

- 删除或替换功能时，检索旧入口、调用方、测试、夹具、快照、辅助代码和文档引用，一并清理失效内容。
- 不为已废弃的行为新增测试，也不为让旧测试通过而保留死代码、旧开关或已下线入口。
- 功能被新契约替代时，删除或改写旧断言，只验证仍然有效的行为；测试名称与注释也必须使用当前术语。
- 仍受支持的兼容格式、权限拒绝、输入校验和安全边界不是废弃功能，其测试不能因“旧”而删除。
- 不能确定某功能是否废弃时，先核对实际调用与当前需求，不以名称或代码年龄自行判定。

## 4. UI 大改必须在 PR 贴前后对比

- 页面布局重做、导航或信息层级调整、列表/表单改版、共享 UI 迁移等明显视觉变化，都要主动提供前后对比，不等用户另行要求；零散文案或微小样式修正不强制，用户要求时仍需提供。
- 先按项目约定启动环境，在真实浏览器中验证渲染、关键交互和计算样式；CI 通过或静态模板检查不能替代运行时验收。环境受阻时明确记录未验证项，不用设计稿或生成图片冒充截图。
- Before 使用明确的 PR base 提交，After 使用当前改动；保持相同角色、演示数据、语言、视口与页面状态，并注明版本。涉及 DOM 或业务逻辑变化时分别运行两版本，不能仅换 CSS 模拟旧版。
- 默认把 **PC 版合成一张 PNG 长图**：左侧调整前、右侧调整后，按页面/状态分区，写清标题与 Before/After，方便直接转发 IM。可裁掉重复导航和无内容留白，但不修改页面内容，也不把文字缩小到无法阅读。
- 覆盖主要受影响页面，以及与改动相关的空态、编辑态等状态；响应式改动另验窄屏，移动端截图单列，不混进默认 PC 长图。
- 将长图作为附件贴到 **PR 正文或评论**，提供原图链接，并简述改动、验证范围和未验证项；发布后确认图片链接确实存在，不能只留本地路径或声称已上传。GitHub 上传方法见 [UI 对比附件](references/ui-comparison.md)。
- 使用演示数据，避免泄露真实用户信息和凭证；优先使用 PR 原生附件，不擅自上传到无关公开图床。截图仍遵守第 1 节，不提交 Git，也不放进源码文档；本规则不额外授权提交、推送或部署。

## 交付前检查

0. 确认任务分支的起始基线来自本次任务 fetch 后的远端目标分支，并已核对提交/推送前的最新远端状态；如有用户明确允许的例外，交付时说明。
1. 查看完整 diff，包括二进制文件、测试辅助方法和生成路径；确认无文档图片入库。
2. 对照当前实现原地更新文档，移除过时叙述、重复内容和失效链接。
3. 确认已删除功能不再有测试或辅助代码继续维护，仍有效的兼容契约有必要覆盖。
4. 在项目规定环境运行受影响测试及必要静态检查；验证不应重新生成文档图片。
5. UI 大改已完成真实浏览器验收，PC 前后对比长图已贴到 PR，原图链接可用；阻塞和未验证项已明确说明。
6. 提交与更新 PR 继续遵守项目的授权规则，不擅自提交、改写历史或部署。
7. 本机环境修复确认未污染团队配置，跨 worktree 可复用；交付说明实际启动验证结果与尚未完成的后台任务。
