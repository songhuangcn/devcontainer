# Development — 开发维护规则

适用于所有项目的开发任务，与项目自身规范及领域 skill 同时执行。

## 0. 开发前同步远端基线

避免在过期代码或过期开发规则上开始工作。每项新开发任务在修改文件前，必须完成以下检查：

- 检查 `git status`、当前分支和 `git worktree list`，识别已有改动、未推送提交及其他会话的工作区；不得覆盖、丢弃或擅自搬移这些工作。
- 执行 `git fetch origin`，确认 origin 的默认主分支（如 `main` / `master`），以本次 fetch 后的 `origin/<主分支>` 为基线；不能把本地同名主分支或未刷新的远端引用当作最新代码。项目明确要求其他目标分支时，以该远端目标分支为准。
- 从该最新远端基线创建本任务的独立开发分支，优先用 `git worktree add -b <任务分支> <新目录> origin/<主分支>` 创建隔离工作树，并将会话工作目录切换过去；不在主分支、部署分支或 detached HEAD 上直接开发。
- 在新工作目录重新读取适用的 `AGENTS.md`、开发 Skill 和相关项目文档，避免继续沿用旧工作树中的规则。
- 当前工作区已有改动时，优先保持原状并另建工作树。需要将已有任务改动迁移到最新基线时，先核对归属和差异；迁移会影响其他工作或无法安全判断时，先向用户确认。禁止为同步基线自动 reset、清理、stash 或强制 checkout。
- 同一任务的后续轮次可以继续使用其开发分支/worktree，无需反复创建。继续开发及提交/推送前再次 fetch，核对目标分支是否前进；如已前进，先评估差异，在保留现有工作的前提下安全同步并复测，不擅自 rebase 已发布提交或强制推送。
- fetch 失败、origin 不存在或目标分支无法确定时，明确告知阻塞；未经用户同意，不以旧基线继续修改。用户明确指定旧提交或要求沿用现有分支时，说明基线偏离后按其要求执行。

## 1. 图片不进入源码文档

- 不向源码文档目录添加或更新截图、照片、渲染图等图片文件，也不在文档中嵌入图片。
- 验证截图存到仓库外临时目录，或项目明确忽略的测试产物目录；需要分享时使用 PR 附件或外部存储，不以提交图片到 Git 代替。
- 不添加把截图写进 `docs/` 等文档目录的脚本、测试辅助方法或环境变量入口；已有此类入口时，在相关改动中删除。
- 业务实际需要的图片资源、测试必需的图像夹具不属于文档截图，不因本规则误删。
- 清理限于当前改动和直接相关的引用；不擅自全仓库删图，也不为清理图片擅自重写 Git 历史。

## 2. 源码文档只描述当前状态

- 优先原地更新已有文档，替换过时段落，不追加“之前怎样、此次怎样、现在修好了”等过程描述。
- 不在源码文档累积变更日志、逐轮测试结果、会话记录、已完成待办或旧实现说明；过程信息放 commit / PR，历史交给 Git。
- 只保留理解当前契约、使用方法、限制和必要设计决策所需的内容，避免跨文档重复。
- 当前仍支持的兼容行为、真实边界和操作指引应保留；不要把它们误判为过程记录。
- 若项目明确要求进行中计划或决策文档，按其约定维护，但不把这些过程搬进现状文档。

## 3. 废弃功能与测试一起删除

- 删除或替换功能时，检索旧入口、调用方、测试、夹具、快照、辅助代码和文档引用，一并清理失效内容。
- 不为已废弃的行为新增测试，也不为让旧测试通过而保留死代码、旧开关或已下线入口。
- 功能被新契约替代时，删除或改写旧断言，只验证仍然有效的行为；测试名称与注释也必须使用当前术语。
- 仍受支持的兼容格式、权限拒绝、输入校验和安全边界不是废弃功能，其测试不能因“旧”而删除。
- 不能确定某功能是否废弃时，先核对实际调用与当前需求，不以名称或代码年龄自行判定。

## 交付前检查

0. 确认任务分支的起始基线来自本次任务 fetch 后的远端目标分支，并已核对提交/推送前的最新远端状态；如有用户明确允许的例外，交付时说明。
1. 查看完整 diff，包括二进制文件、测试辅助方法和生成路径；确认无文档图片入库。
2. 对照当前实现原地更新文档，移除过时叙述、重复内容和失效链接。
3. 确认已删除功能不再有测试或辅助代码继续维护，仍有效的兼容契约有必要覆盖。
4. 在项目规定环境运行受影响测试及必要静态检查；验证不应重新生成文档图片。
5. 提交与更新 PR 继续遵守项目的授权规则，不擅自提交、改写历史或部署。
