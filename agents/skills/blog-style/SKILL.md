# 博客写作风格：hdgcs.com

## Overview

复刻 hdgcs.com 的技术博客风格：**实践总结型长文**。核心特征是「三段式骨架 + 图表逐条解读 + 给明确结论」——不是教程搬运，也不是理论综述，而是「我做过这件事，这是我总结的经验，你可以直接照做」。

站点用 VitePress，正文为 Markdown，支持 mermaid 图表。

## 何时用

- 用户要写技术博客、经验总结、方案记录、源码分析、上手教程
- 用户要把草稿/笔记改写成博客文章
- 用户要审校一篇文章是否符合这个风格

## Workflow

### 1. 确认选题类型

先判断属于哪一类，套用对应骨架：

| 类型 | 例文 | 骨架 |
|---|---|---|
| **经验总结**（最常见） | 《GitLab 二次开发》《如何做好一个软件项目》 | 按**阶段/维度**切 2–4 块 |
| **技术原理** | 《gRPC 的高性能和高可用》 | 按**特性/结论**切块，每块一个原因 |
| **源码分析** | 《Gin 源码分析概览》《Gin 源码分析 - 路由》 | 按**调用链顺序**切块，用「一、二、三」编号 |
| **上手教程** | 《Kubernates 快速上手》 | 按**动手步骤**切块：准备 → 搭建 → 配置 → 部署 |
| **工具/方案记录** | 《我的 NAS 家庭存储方案》 | 按**需求**切块，一个需求一个方案 |
| **生活体验** | 《新能源汽车全方位体验》 | 按**阶段**切块，标题带「篇」字，给真实数据 |

### 2. 先定三段式骨架

**这是本风格最核心的特征**：正文必须被切成 2–4 个平行大块，且**开篇引言就要点名这几块**。

真实例子：

- GitLab 二次开发 → 开发阶段 / 部署阶段 / 维护阶段
- 如何做好一个软件项目 → 项目环境和文档 / 项目管理 / 项目代码
- gRPC → 高性能 / 高可靠
- 新能源汽车 → 购车篇 / 用车篇 / 成本篇
- NAS → 设备选购 / 家庭影音 / 家庭相册 / 同步网盘 / 外网访问 / 数据安全

大块之间要平行、无重叠、能覆盖全题。定不出骨架就别动笔。

### 3. 写开篇引言（1 段，3–5 句）

固定包含四件事，顺序基本不变：

1. **一句领域定义或背景** —— 「gRPC 是 Google 在 2015 开源的 RPC 框架」「RPC 是一种远程过程调用协议，目标是让远程服务调用更加简便、直观」
2. **为什么值得写** —— 普遍痛点或普遍需求：「很多企业有进行二次开发的需求」「软件项目大部分是维护多开发少」
3. **本文覆盖什么** —— 显式点名后面的几个大块：「这里从开发、部署、维护三个阶段总结了一些实际经验」
4. **一句期望收尾** —— 从这几个里挑：`希望对你有帮助` / `希望对你有用` / `供参考` / `或许本文可以给你一些帮助` / `本文将为你解答这些疑问` / `我们来具体看下它是如何做到的`

变体：用设问收束第 2 步 →「那如何能做好一个软件项目呢？」

反面：不要写「在当今这个飞速发展的时代」这类空转开头，不要预告「本文将分为 X 章」这种目录式说明。

### 4. 写正文章节

#### 标题层级

- `##` 大块（2–4 个），名词短语。经验总结常带后缀「阶段 / 篇 / 管理 / 方案」
- `###` 子话题，同样是名词短语
- `####` 只在超长文里用（教程、体验类）
- 源码分析的大块用中文序号：`## 一、创建 Engine 对象`
- 讲解型文章可以用「关注点一：测试分层要尽量少」这种带结论的标题

#### 图 + 逐条解读（高频模式，务必用上）

先一句引出，插图，再逐条解释图里的元素：

```markdown
我们先来看下 CPU 指标检测（指标名称叫 profile），下面是具体的函数使用流程图：

<mermaid 流程图>

对于流程图的函数：

- `runtime.SetCPUProfileRate`: 设置采样频率，这个是可选步骤，单位是 Hz，默认值为 100。
- `runtime/pprof.StartCPUProfile`: 启用一个新的 Goroutine 负责执行 CPU 概要信息的收集和输出，参数为一个 io 句柄
```

引出句模板：`下面是具体的 xxx 流程图：` / `xxx 的函数使用流程图为：` / `类似上面两个指标，流程图为：` / `网络图大致为：` / `下面分别是两种树的结构图：`
解读句模板：`对于流程图的函数：` / `说明：` / `其中：`

流程/时序/分支用 **mermaid 内联**（flowchart、gitGraph、sequenceDiagram）；脑图/架构总览用**图片**。

#### 表格用于方案对比

固定的几种列头：

```markdown
| 方案 | 优点 | 缺点 |
| 标准库 | 主要作用 | 使用场景 |
| 名称 | 简写 | 解释 |
| Git 工作流 | 说明 | 适用场景 |
```

给了对比表之后，**必须紧跟一句选择建议**：「我的建议是根据项目需要逐步演进，最终使用功能分支 + 环境分支/标签这种适用性广且操作清晰的工作流。」

#### 有序 vs 无序列表

| 用有序列表 `1.` | 用无序列表 `-` |
|---|---|
| 有先后顺序的步骤、操作流程 | 并列的要点、优缺点 |
| 按时间发生的事（事故处理过程） | 参数/字段说明 |
| 图表元素的逐条编号解读 | 清单、可选项 |

列表项可以写长句甚至带括号补充，不必强求短；但列表前必须有一句引出（以 `：` 结尾）。

#### 代码块

- 必带语言标注：`go` `bash` `ruby` `yaml` `haml`
- 引用第三方源码时，首行注释给出**带 tag 和行号**的精确 URL：

```go
// https://github.com/gin-gonic/gin/blob/v1.9.1/gin.go#L183
func New() *Engine {
    // ...
}
```

- 省略无关代码用 `// ...`
- 示例代码里用注释标注对应的正文章节：`// 一、创建 Engine 对象`

### 5. 写总结（必有）

`## 总结` 或 `## 总结和建议`，包含：

1. 一句回顾，重述三段式骨架：「主要包括"项目环境和文档"、"项目管理"和"项目代码"三个方面：」
2. **一张总结导图**（脑图，覆盖全文结构）——这是本博客的招牌
3. 一句拔高的观点或落地建议收束

可选的收尾方式，挑一种：

- **观点收束**：「总结起来，就是对 GitLab 做二次开发，需要有一套健壮的开发流程，一个方便快捷的部署方案以及有一些可靠稳健的维护手段。」
- **落地建议**：「在我们的项目中，建议尽可能充分利用 gRPC 的以上特性来提升我们的程序。」
- **进阶方向清单**（源码分析常用）：「如果想继续深入，以下是一些推荐的方向：」+ 列表
- **轻松一笔**：「最后关于成本问题，借用一句话"骑自行车去酒吧，该省省该花花"。两千的 NAS 可以，二十的视频会员不行！」
- **自我推广 + 邀请讨论**：「打个广告，我当前开源了一个管理系统模板的开源项目：xxx…如果你有关于软件项目好的实践或想法，欢迎一起讨论。」

有外部参考时，最后加 `## 扩展阅读`，纯链接列表，不加评语。

## 语气规则

### 人称

- **「我」** 讲亲身经历、选择理由、局限：「我的体验是基本也是可以完成开发工作的」「我用车经验不多」
- **「我们」** 带读者一起推演：「我们先来看下」「综上，我们想做二次开发并保持上游同步，我们需要这么做」
- **「你」** 直接给建议：「如果你愿意折腾，对网络要求高，可以使用 DDNS 直连方案」

### 必须给明确结论

不模棱两可。用这些句式：

- `我的建议是…` / `我推荐用上：` / `我的推荐是：`
- `建议你买特斯拉，因为它最稳妥`
- `这个没什么好说的，可以直接通过钞能力解决`
- `一般的系统要求建议完成全量备份即可`
- 分级建议：「一般 X 就够了…不过如果 Y 的确很吸引你，就可以尝试了」

### 自问自答 / 预判读者反驳

这是本风格的显著特征，每篇至少用 1–2 次：

- 「上述流程第一次见会觉得有点复杂？但实际上这已经是最精简的了，我们可能见过很多团队…」
- 「我们可能有疑问为什么不直接在路由器上转发到 DSM 服务地址，这是因为我们需要用到 NAS 的 SSL 证书功能」
- 「可能会有人说我缺少了这种类型也没关系吧，反正 xxx 的单元测试里面测试全就行吧？其实不是的，因为…」
- 「还有关于端口的使用，太多端口了记不住，能否外网也统一用服务默认端口比如 5000？其实也是可以的，只需要…」

### 排版细节

- 中英文之间加空格：`GitLab 二次开发`、`使用 Docker 简化部署`
- 数字与中文单位紧贴（**不加空格**）：`20分钟`、`12度/百公里`、`9000元`、`3秒`、`2台`
- 数字与英文单位加空格：`120 km`、`18T`、`2C4G`
- 补充说明用**半角括号** `()`：`切出版本分支(命名 xxx-stable-ee)`
- 界面名词、专有概念用**中文引号** `“”`：`“控制面板” -> “外部访问” -> “QuickConnect”`
- 术语首次出现给英文原名：`前缀树(Trie)`、`基数树(Radix Trie)`、`模型层，有时也叫做实体层（Entity）`
- 行内代码标记命令、文件名、字段、分支名：`` `master-my` ``、`` `docker-compose.dev.yml` ``、`` `node.getValue` ``
- 外链用内联 markdown，优先指向**官方文档**，链接文字就是文档标题
- 给具体版本号：`v1.9.1`、`群晖(7.x)`、`GitLab 17.10.3`
- 不用 emoji

## 内容准则

1. **只写做过的事**。给真实数字：里程、能耗、费用、耗时、容量、配置、版本号。没有真实数据就别硬写这一段。
2. **讲「为什么这么选」不只讲「怎么做」**。每个方案后面要有取舍分析。
3. **每个概念落到「我们应该怎么做」**。不写纯理论。
4. **承认局限**：「我用车经验不多，本身没有那么多过去经历做对比」「具体算法细节有兴趣的可以深入方法查看」——不假装全知。
5. **篇幅**：正文 4000–14000 字符，多数落在 8000–13000。短文（gRPC 4127 字符）只写一个技术点，长文（软件项目 14353 字符）覆盖完整方法论。
6. **配图 1–3 张**，其中结尾的总结导图几乎必备。

## 反模式

- ❌ 空转开头（「在当今飞速发展的时代」「随着技术的不断进步」）
- ❌ 目录式预告（「本文将分为五个章节，第一章…」）——骨架靠引言那一句话点名即可
- ❌ 只罗列不给结论的对比
- ❌ 营销腔（「炸裂」「颠覆」「revolutionary」「必看」「99% 的人都不知道」）
- ❌ emoji
- ❌ 通篇「我们」而没有「我」的真实经验
- ❌ 引用源码不给精确 URL（要带 tag 和行号）
- ❌ 没有 `## 总结`
- ❌ 编造数据、编造踩坑经历

## 审校清单

改写或审校时逐项对照：

- [ ] 引言 3–5 句，含背景 / 痛点 / 覆盖范围 / 期望收尾
- [ ] 正文切成 2–4 个平行大块，且引言点名过
- [ ] 至少 1 处「图 + 逐条解读」
- [ ] 方案对比用了表格，且表格后紧跟选择建议
- [ ] 至少 1 处自问自答或预判读者反驳
- [ ] 有序/无序列表用途分明
- [ ] 代码块带语言标注；源码引用带精确 URL
- [ ] 有明确结论句（「我的建议是」类）
- [ ] 有 `## 总结` + 总结导图 + 收束句
- [ ] 中英文空格、数字单位、括号引号符合规则
- [ ] 全文有真实数字，没有编造内容

## 文件约定

站点为 VitePress，文章放在 `posts/` 目录，命名 `<序号>-<英文-短横线-slug>.md`，例如：

```
posts/37-gitlab-secondary-development.md
posts/36-kubernates-tutorial.md
posts/35-new-energe-experience.md
```

图片放 `/assets/`，正文中用 `![描述](/assets/xxx.png)` 引用。序号取当前最大值 +1。
